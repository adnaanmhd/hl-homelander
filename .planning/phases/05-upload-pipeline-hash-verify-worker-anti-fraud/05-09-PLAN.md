<objective>
Gap closure for CR-02 (the server side of the CR-01/CR-02 pair). `POST /recordings/init` is currently non-idempotent — it always `CreateMultipartUpload`s + `INSERT ... onConflictDoNothing()`, so a duplicate `/init` (the retry path the mobile coordinator takes on a process-kill / presigned-TTL expiry) leaves the row's `s3UploadId` as the FIRST one while the response binds to a SECOND fresh upload → `/finalize` 409s/`NoSuchUpload`s on the stale `s3UploadId` → the recording is permanently un-finalizable, and a stray multipart upload leaks per duplicate call. This plan makes `/init` SELECT-first + idempotent, and adds a `POST /recordings/:id/parts` re-presign route (no `CreateMultipartUpload`) that the mobile coordinator (Plan 05-10) calls on a re-drain instead of `/init` — preserving the already-uploaded parts' ETags (the slow-cellular resume guarantee, UP-04).

Purpose: UP-01 (the upload lifecycle survives retries — `/finalize` always uses the upload id the client uploaded against), UP-04 (no whole-file restart — already-DONE parts keep their ETags because the upload id doesn't change). This is the **server half**; the mobile coordinator's "call `/recordings/:id/parts` on a re-drain instead of re-`/init`" change is Plan 05-10 (wave 2, depends on this route existing).
Output: an idempotent `init.ts` + the new `parts.ts` route + the route registration + the new shared-types schemas + the two Vitest specs.
</objective>

| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| client → `POST /recordings/init`                                       | the caller's JWT (`sub`) gates ownership; `recordingId` / `partsCount` / SHAs are client-supplied — a duplicate `/init` is the retry path, must not corrupt the row's `s3UploadId`                                 |
