## Defense-in-Depth Notes

These are protections that go beyond the strict mitigation plans in the threat register — captured here so future audits don't accidentally regress them:

- **Hydrate-side validation backstop.** `apps/mobile/src/state/hydrate.ts:55` runs `CompatResultSchema.safeParse(JSON.parse(...))` on hydrate, clearing the slot when validation fails. This backstops T-2.3-01 / T-2.14-01 / T-2.15-01 (all `accept` dispositions) without changing their disposition.
- **Crashlytics regression-guard.** `apps/mobile/scripts/verify-merged-manifests.sh:163-178` adds a `firebase_crashlytics_collection_enabled="false"` regression-guard. The SDK isn't yet integrated (see DR-2-01) but the guard is forward-compatible: when Crashlytics lands at Phase 4 last wave, the existing gate immediately covers the opt-out attack surface.
- **upgradeFlow structural guard (Pattern 50).** `apps/mobile/src/services/upgradeFlow.ts:84-108` structures the apkRollout flow so `launchInstaller` is only reachable inside the success branch of `downloadAndVerifyApk`. T-2.20-01 thus has a structural mitigation in JS layered atop the Kotlin SHA-256 gate.
- **Re-entrancy guard on destructive modals (Pattern 66, quick-260510-006).** `DeleteAccountModal.tsx` + `LogoutModal.tsx` use a `useRef`-backed synchronous guard, released only on error. Prevents a fast double-tap from firing a second DELETE /me after the first call's signOut clears the JWT. Indirectly hardens T-2.19-\* against the misleading-error UX class.
