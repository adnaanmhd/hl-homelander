## Investigation plan (verbatim — first action when resuming)

1. **Read DeviceCaps.kt.** Find where it picks the cameraId for the ultrawide measurement. Look for: `cameraManager.cameraIdList`, `LENS_FACING`, `LENS_INFO_AVAILABLE_FOCAL_LENGTHS`, `SENSOR_INFO_PHYSICAL_SIZE`, `LENS_POSE_REFERENCE`, `multi-camera` / `LOGICAL_MULTI_CAMERA` characteristics. The bug is likely either:
   - (a) Picking `cameraIdList[0]` blindly (which is usually the main wide, not the ultrawide)
   - (b) Filtering by `LENS_FACING=BACK` but stopping at the first match (still the main wide)
   - (c) Computing dFOV with the wrong formula or wrong sensor dimension axis (would explain Pixel 7a's 134.7° — too high — vs Pixel 10a's 83° — too low; same camera but wrong arithmetic on different sensor sizes)
2. **Read DeviceCapsTest.kt.** See how the failing test sets up the Pixel 7a fixture. Compare what the test EXPECTS (118-122°) vs what production CODE returns (134.7°). The test fixture probably mocks specific sensor dimensions + focal lengths — verify the formula matches dFOV = `2 * atan(diagonal_sensor_size / (2 * focal_length))`.
3. **Decide root cause.** Wrong-camera selection (most likely given the 83° vs 134.7° asymmetry) OR wrong-formula (less likely; would produce consistent over/under-shoot).
4. **Apply fix.** Iterate ALL back-facing cameras, compute dFOV for each, pick the MAX. That should be the ultrawide on Pixel 7a / 8a / 10a.
5. **Update DeviceCapsTest.kt** to cover the camera-iteration logic (add a test case with 2 back cameras: main 78° + ultrawide 120°; assert the picker returns 120°).
6. **Rebuild + reinstall + re-test.**
