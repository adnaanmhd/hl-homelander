**Camera handoff (gate ↔ active recording)**

- **D-CAM-01:** Gate uses `react-native-vision-camera@4.7.3` (preview + `takePhoto()` only — the locked CLAUDE.md / STACK pin). Active recording hands off to HumynCapture (Camera2, Phase 3). ## Summary

Phase 4 assembles the recording surface end-to-end on top of Phase 3's `HumynCapture` Camera2+MediaCodec module. The genuinely novel technical pieces are: (1) `HumynHandDetector` — a ~95-LOC Kotlin native module wrapping MediaPipe `HandLandmarker` in `RunningMode.IMAGE` (single-frame, hand-count only), a near-verbatim port of Figure's reverse-engineered pattern in `figure-app-hands.md`; (2) a `react-native-vision-camera@4.7.3` preview-and-`takePhoto()` gate substate that hands camera ownership to HumynCapture on gate-pass, with the handoff latency masked by a TTS "Recording started" line; (3) the `recState` state machine (shape fixed in `engineering-handoff.md §4.3` — reproduced verbatim below) covering rotate-prompt → ready → pre-flight → gate(loading/waiting/confirmed) → active → stop-confirm → stopped; (4) a `useRecordingLifecycle` hook implementing the `idea-brief.md §10` policy table over AppState / orientation / audio-focus / battery / storage; (5) three more tiny in-house Kotlin modules (`HumynPhoneState`, `HumynBattery`, `HumynScreenBrightness`); and (6) the practice-tutorial flow with a once-per-install-per-Google-account MMKV gate.

The dominant risk is **the ±1 ms video↔IMU drift invariant** (the project's non-negotiable, the reason audio was dropped — CLAUDE.md banner; Phase 3 smoke 7 measured mean 0.594 ms / p99 0.728 ms). Phase 4 does not change HumynCapture's encoder, but it introduces a NEW moment where camera ownership transfers (VC → HC) under a TTS-masked time budget; drift must be re-measured at the gate→record handoff on hardware. The second-largest risk — and the biggest correction from the prior research pass — is **phone-call detection**: `TelephonyManager.registerTelephonyCallback()` / `PhoneStateListener.LISTEN_CALL_STATE` **requires `READ_PHONE_STATE`** on apps targeting API 31+ (which this is — `targetSdk 35`), and CLAUDE.md forbids that permission. So phone-call detection must run **entirely off `AudioManager.OnAudioFocusChangeListener`** (no telephony API at all), which also covers alarms — but with a coarser signal (audio-focus loss/gain transitions, not call states), so the call-answered-vs-declined distinction becomes a timing heuristic, not a state read. The third risk is **OEM phone-state / battery-manager / camera quirks** (Xiaomi MIUI, Oppo/Realme ColorOS, Vivo FunTouch) — `.planning/research/PITFALLS.md` Pitfalls 7 and 8 are the canonical catalog.

**Primary recommendation:** (a) Re-measure drift on hardware (Pixel 10a / 7a-class) for the gate→record handoff before Phase 4 closes — it is a [BLOCKING] manual gate. (b) Drop the `TelephonyCallback` plan entirely; build `HumynPhoneState` as a pure `AudioManager` audio-focus listener (no `READ_PHONE_STATE`). (c) Port `HumynHandDetector` verbatim from `figure-app-hands.md` + STACK.md recipe §3 — do not improvise on MediaPipe config. (d) Use `react-native-svg` (already a dep) for the 130×130 progress ring rather than pulling Skia into the ring path (Skia is still needed only if/when a VC frame-processor is added — which D-CAM-04 explicitly rejects, so Skia may not be strictly required this phase; planner confirms). (e) Keep `recState` as a `useReducer` inside RecordingScreen. (f) Wire all four new Kotlin modules off the Phase-3 `HumynCompatModule.kt` / `HumynCaptureModule.kt` ergonomic templates and register them in `MainApplication.kt`. (g) Build `start(opts)` carefully — the `CaptureSessionOpts` schema (Phase 3 D-API-02) is **richer than the prior research assumed**: it requires `taskCategory`, `taskSetting`, a full `contributor` object, `location`, `appVersion`, `dfovDegrees`, and a structured `startGate` with `{type:'hand_detection', passed, skipped, bypassed, durationMs, consecutiveHitsRequired, platformCadenceMs}`.

### `recState` shape — VERBATIM from `engineering-handoff.md §4.3`

> This is the canonical shape. The prior research's field list (`gate.phase`, `consecutiveHits`, `targetHits`, `cadenceMs`, `skipped`, `bypassed`) was correct but incomplete — here is the full type:

```typescript
type RecState = {
  taskId: string;
  taskName: string;
  isPractice: boolean;
  startedAt: number | null; // performance.now (active recording start)
  durationMs: number;
  cap: 60_000 | 1_200_000; // practice = 60s, real = 20m  (NB: HC's own auto-segment is 10-min; the 20m "cap" here is the §4.3 doc value — JS owns ONLY the practice 60-s hard cap; real recordings have no JS-side cap, HC auto-segments)
  ended: boolean; // double-stop guard
  alerts: { battery?: boolean; thermal?: boolean };
  gate: {
    phase: 'idle' | 'loading' | 'waiting' | 'confirmed';
    consecutiveHits: number; // count===2 streak; resets to 0 on any miss
    targetHits: number; // 5 on Android (× 400 ms cadence) / 3 on iOS (× 600 ms) — from Remote Config gate.consecutive_hits_required
    cadenceMs: number; // 400 on Android / 600 on iOS — from Remote Config gate.cadence_ms
    skipped: boolean; // true if user tapped Skip
    bypassed: boolean; // true if HandDetector native module was unavailable
    startedAt: number | null; // performance.now (gate enter)
    confirmedAt: number | null; // performance.now (gate exit, success/skip/bypass)
  };
};
```

The `gate` block survives onto the metadata JSON as `metadata.start_gate` (`§7.3` / `video_metadata.json`) — but note Phase 3's `CaptureSessionOpts.startGate` schema is the _transport_ shape: `{type:'hand_detection', passed:boolean, skipped:boolean, bypassed:boolean, durationMs:number, consecutiveHitsRequired:number, platformCadenceMs:number}`. The reducer's `gate` sub-object maps onto that at `start()` call time: `passed = gate.phase==='confirmed' && !skipped && !bypassed`, `durationMs = confirmedAt - startedAt`.

`recState` substate enum (derived from the §4.3 diagram — the diagram names states, not a single discriminated field; the planner reproduces it as a `substate` discriminant): `'rotate-prompt' | 'ready' | 'pre-flight' | 'gate' | 'active' | 'stop-confirm' | 'stopped'`. `gate.phase` is a sub-discriminant within the `'gate'` substate. `'thermal-alert'` and `'battery-alert'` from the diagram are overlay flags on `alerts`, not separate substates (recording continues underneath).

### Pattern 1: Photo-to-disk hand-gate poll loop (D-CAM-04 / HAND-03/04/13)

**What:** In the `gate.waiting` phase, every `gate.cadenceMs` ms: call VC `camera.takePhoto({flash:'off', enableShutterSound:false})` → `RNFS.moveFile(photo.path, ${RNFS.CachesDirectoryPath}/hand-gate/${ulid()}.jpg)` → `HumynHandDetector.detectHands(dest)` → if return `=== 2` dispatch `GATE_HIT` else `GATE_MISS` → `RNFS.unlink(dest)` in a `finally` (swallow errors). On `consecutiveHits >= targetHits` → dispatch `GATE_CONFIRMED`.

**Important detail (corrected):** In VC 4.7.x, `qualityPrioritization` is a **prop on `<Camera>`** (`photoQualityBalance="speed"`), not a per-call `takePhoto()` option. Set `photoQualityBalance="speed"` and `photo={true}` on the Camera. `takePhoto()` returns `PhotoFile { path, width, height, orientation, isRawPhoto, ... }` — `path` is a temp path you must move/copy. There is also `takeSnapshot({quality})` (grabbed from the preview, ~16 ms, much faster than `takePhoto()`) — Figure used `takePhoto()` and the spec says `takePhoto()`, so stay with `takePhoto()`, but the planner could note `takeSnapshot` as a latency fallback if cold-start `takePhoto()` proves too slow on ₹30K devices.

**When to use:** The `gate.waiting` phase only. Stop the loop on transition out (`confirmed` / `skipped` / `bypassed` / screen unmount / X-dismiss). Use a `useEffect` + `setInterval`/recursive-`setTimeout` keyed on `recState.substate === 'gate' && recState.gate.phase === 'waiting'`; clear it in the cleanup.

### Pattern 2: TTS-masked camera handoff (D-CAM-02)

**What:** The `gate.confirmed → active` transition reassigns camera ownership from VC to HumynCapture. VC tear-down + Camera2 close + HC `start()` is ~300–500 ms — long enough to look like a stall. Sequence (numbers are starting points; tune on Pixel 7a/10a hardware in Wave 5):

```
1. dispatch GATE_CONFIRMED  (recState.gate.phase = 'confirmed')
2. if (passed)  Vibration.vibrate(80)               // 80 ms haptic, front-loads the perception
3. if (passed)  await pickAndSetEnInVoice() once if not already set ; Tts.speak('Recording started.', {androidParams:{KEY_PARAM_VOLUME:0.85}})
4. await HumynScreenBrightness.set(0.05)            // brightness drop to 5%
5. setCameraActive(false)                            // <Camera isActive={false}> — VC releases Camera2 (VC has no explicit unmount(); conditional-render or isActive=false is the API)
6. await new Promise(r => setTimeout(r, ~80))        // [TUNABLE] let Camera2 close complete — adjust if start() stalls
7. try {
     const r = await HumynCapture.start(opts)        // HC opens Camera2 — resolves when encoder pipeline is up
     dispatch({type:'CAPTURE_STARTED', ...r})        // → recState.substate = 'active'
   } catch (e) {
     Tts.speak(e.code === 'thermal_throttling' ? 'Phone too warm.' : 'Could not start recording.')
     await HumynScreenBrightness.set(-1)              // restore brightness
     dispatch({type:'CAPTURE_START_FAILED', error:e})// → recState.substate = 'ready'
   }
```

**Critical:** This is the moment to re-measure ±1 ms drift. `HumynCapture` owns drift, but "camera-was-just-released-by-another-process" is a new condition in Phase 4. **Re-measure on hardware** (read `onSegmentComplete.drift.{max,mean,p99}` for the first few segments of a gate-started recording; must not regress Phase 3 smoke 7's mean 0.594 / p99 0.728 ms). If `start()` ever needs a settle delay before Camera2 is reliably free, step 6 is the tuning knob; if even that isn't enough, the planner escalates a "HC.start() should poll for camera availability" change to Phase 3 (surgical-stage protocol).

### Pattern 3: §10 lifecycle policy table → `useRecordingLifecycle` hook (D-LIFE-01)

Reproduced from `idea-brief.md §10` (the canonical table — read it directly; this is the mapping):

```
EVENT (source)                                          → POLICY
─────────────────────────────────────────────────────────────────────────────────────────────────────────────
User exits recording screen mid-record (X→Stop modal→Stop) → stop()    // upload if ≥60s, else discard
User backgrounds the app mid-record (AppState 'background') → stop()    // upload if ≥60s, else discard
User force-quits the app mid-record                        → no JS hook fires; HumynCapture FGS finalizes orphan;
                                                             recovery on next launch (D-LIFE-04) — upload if ≥60s
User uninstalls mid-record / mid-upload                    → recording lost (nothing to do)
No internet during/after recording                         → stored locally, Phase 5 auto-resumes (no Phase 4 action)
No internet + storage full                                 → recording lost; user notified (HC onError 'storage_full' → stop()+toast)
Phone rotates to portrait/inverse-landscape mid-record     → stop()    // toast "Recording stopped — keep the phone in landscape."
Incoming call ANSWERED (audio-focus: sustained LOSS / LOSS_TRANSIENT not quickly regained) → stop()  // upload if ≥60s
Incoming call DECLINED (audio-focus: LOSS_TRANSIENT then GAIN within ~a few seconds)        → no-op (recording continues)
Notifications during recording                             → no-op (per device settings; no in-app DND nudge; REC-09)
Alarm rings during recording (audio-focus: LOSS_TRANSIENT, alarm stream) → stop()  // upload if ≥60s (alarm can't be suppressed)
Battery ≤15% (HumynBattery transition)                     → alert+continue()  // toast "Battery low. Consider charging soon." + 520Hz/200ms beep + Vibration.vibrate([0,100,50,100]) + Tts.speak + alert pill ; recording continues
Battery ≤5% (HumynBattery transition, mid-record)          → stop()    // end current segment immediately
Battery <5% at recording START (start guard)               → refuse-new()  // toast ; allow again at ≥15%
Storage <5GB at recording START (REC-16 start guard)       → refuse-new()  // toast "Not enough storage to record"
Storage write failure mid-record                           → HC emits onError({code:'storage_full'}) → stop()+toast
Pre-record thermal ≥THROTTLING                             → HC.start() rejects with 'thermal_throttling' → toast (pre-flight substate → ready)
Mid-record thermal ≥THROTTLING_SEVERE                      → HC emits onThermalAbort → Tts.speak("Phone too hot, stopping recording") + thermal alert pill + 440→560→680 Hz tones + Vibration.vibrate(800) ; HC self-stops within ~2.5s ; on stopped → toast "Recording stopped — phone needs to cool."
App OS-evicted from memory mid-record                      → FGS auto-restarts; fragmented MP4 salvageable to last 30-s flush (HC owns this); recovery toast on relaunch (D-LIFE-04)
Logout while a recording is active                         → stop(); preserve upload queue (Phase 5 owns the queue)
Permission revoked (Camera/Mic) mid-record                 → HC emits onError({code:'permission_revoked'}) → stop()+re-prompt
Same Google account on a new device                        → re-runs full compat check (Phase 2 territory; not Phase 4)
```

The "answered vs declined" distinction is the one place this gets fuzzy with audio-focus (vs the old call-state read). Recommended heuristic: on `AUDIOFOCUS_LOSS_TRANSIENT`, start a ~6–8 s timer; if `AUDIOFOCUS_GAIN` arrives before it fires → treat as "declined / brief interruption" → no-op; if the timer fires (focus still lost) OR an `AUDIOFOCUS_LOSS` (permanent) arrives → treat as "answered / alarm" → `stop()`. This errs toward stopping (data-safety bias) and matches the §10 spirit. Tune the timeout in Wave 5 on real hardware with real calls/alarms.

### Pattern 4: en-IN female TTS voice selection (REC-14 / `engineering-handoff.md §6.3` / `idea-brief.md §13`)

**What:** `react-native-tts@4.1.1` exposes `Tts.voices()` → array of `{id, name(iOS only), language(BCP-47), quality(300|500), latency(100-500, Android), networkConnectionRequired(bool, Android), notInstalled(bool, Android)}`. No gender field — match on `language` + name heuristics. Chain: (1) `language==='en-IN'` & name/id looks female (Android system en-IN voices have ids like `en-in-x-end-network` / `en-in-x-ene-local`; female-leaning ones aren't reliably labelled, so the heuristic is weak — fall through quickly) → (2) any `language==='en-IN'` → (3) `language==='en-US'` & female-ish → (4) first `language?.startsWith('en')`. Filter out `notInstalled` voices first. Apply once at app or RecordingScreen init via `Tts.setDefaultVoice(id)` after `await Tts.getInitStatus()`.

**⚠ CORRECTION (rate scale):** `idea-brief.md §13` says "rate 1.0, pitch 0.95, volume 0.85" but `react-native-tts`'s `setDefaultRate(rate)` expects a cross-platform-translated value in `0.01–0.99` (passing `1.0` is out of range); a "normal" rate is roughly `0.5`. To get the spec's intent (normal speed), call `Tts.setDefaultRate(0.5)` (translated) — OR `Tts.setDefaultRate(1.0, true)` with `skipTransform=true` to pass through to Android's raw `1.0` (which IS normal speed on Android `TextToSpeech.setSpeechRate`). **Recommend `setDefaultRate(1.0, true)` on Android** (raw passthrough; matches the spec literally). `setDefaultPitch(0.95)` is fine (Android `TextToSpeech.setPitch` accepts it). Volume: there is no `setDefaultVolume`; pass `androidParams:{KEY_PARAM_VOLUME: 0.85}` per `speak()` call.

### Pattern 5: Once-per-install-per-Google-account tutorial gate (ONB-08, D-NAV-04)

### Pattern 6: Crash-recovery boot listener (D-LIFE-04)

### Anti-Patterns to Avoid

- **Using `TelephonyManager` / `PhoneStateListener` for call detection** — needs `READ_PHONE_STATE` on API 31+ (forbidden by CLAUDE.md). Audio-focus only.
- **Requesting `READ_PHONE_STATE` or `ACCESS_NOTIFICATION_POLICY`** — CLAUDE.md forbids both; no DND toggle (REC-09).
- **Driving the gate from a VC frame processor instead of `takePhoto()`-to-disk** — D-CAM-04 mandates the photo-to-disk path.
- **Extending HumynCapture to expose a preview surface** — D-CAM-01: HumynCapture stays single-responsibility.
- **Concurrent camera access** — VC and HumynCapture must never hold Camera2 at the same time. Strictly sequential: VC `isActive=false`/unmount → await close → HC `start()`.
- **Re-running the hand-gate at 10-min auto-segment cuts** — CAP-10 / Phase 3 D-SEG-01: the `start_gate` block is preserved across all segments; the gate runs once per session.
- **Re-encoding / touching the MP4/CSV/JSON** — Phase 4 never touches captured files in transit (CAP-18); it only calls `start()`/`stop()` and reads event paths.
- **Re-introducing audio capture** — dropped 2026-05-11; re-introducing requires on-hardware proof drift stays inside ±1 ms.
- **Sharing `recState` globally via Zustand "just in case"** — keep it screen-local (`useReducer`) unless a concrete cross-surface reader exists.
- **`Settings.System.SCREEN_BRIGHTNESS` for the 5% dim** — that needs `WRITE_SETTINGS` and persists OS-wide. Use the per-window `WindowManager.LayoutParams.screenBrightness` override (no permission; resets on window destroy).
- **Lowering gate `targetHits` / `minHandDetectionConfidence` in code to "make it pass"** — Phase-2 wave anti-pattern; tune via Remote Config (HAND-11) post-launch, never in code.
- **Skipping drift re-measurement on the new handoff** — the ±1 ms invariant is non-negotiable; it's a [BLOCKING] manual gate.
- **Building the 60-s practice hard-cap inside HumynCapture** — HC's own segment timer is 10-min; the 60-s practice cap is JS-owned (`recState`: call `HumynCapture.stop()` at `t≥60_000 ms` when `isPractice`).

## Common Pitfalls

### Pitfall 1: ±1 ms drift regression on the camera handoff

**What goes wrong:** After VC releases Camera2 (`isActive=false`/unmount), `HumynCapture.start()` opens it again; if Camera2 isn't fully released yet, `start()` may stall, retry internally, or initialize with a different timestamp-base alignment — pushing `imu_video_drift_{mean,p99}_ms` outside ±1 ms (the exact failure mode that killed audio). Phase 3 smoke 7 measured mean 0.594 / p99 0.728 ms with no preceding camera owner — that headroom may shrink when VC just released the device.
**Why it happens:** Camera2 `close()` is async; "VC `isActive=false`" ≠ "camera HAL released". Pattern 2's step-6 settle delay is a guess.
**How to avoid:** On Pixel 10a / 7a-class hardware (Wave 5), run the gate→record path repeatedly and read `onSegmentComplete.drift.{max,mean,p99}` for the first few segments of gate-started recordings. If any segment exceeds ±1 ms, increase the settle delay (Pattern 2 step 6) or escalate a "HC.start() polls for camera availability" change to Phase 3. Make the settle delay a tunable constant. **This is a [BLOCKING] manual gate before phase verification.**
**Warning signs:** `start()` Promise resolves slowly (>800 ms); first-segment drift figures noticeably worse than steady-state segments.

### Pitfall 2: Phone-call detection via the telephony API throws `SecurityException` (the prior research's D-LIFE-02 plan)

**What goes wrong:** Registering `TelephonyCallback.CallStateListener` (or `PhoneStateListener.LISTEN_CALL_STATE`) without `READ_PHONE_STATE` throws `SecurityException` on apps targeting API 31+. This app is `targetSdk 35`. CLAUDE.md forbids `READ_PHONE_STATE`. So the entire "use TelephonyCallback, fall back to PhoneStateListener for 26–30" plan is unbuildable.
**Why it happens:** Android 12 (API 31) tightened call-state access; the permission-free era of `LISTEN_CALL_STATE` (state-only, no number) ended.
**How to avoid:** Build `HumynPhoneState` purely on `AudioManager.OnAudioFocusChangeListener` (request `AUDIOFOCUS_GAIN` via an `AudioFocusRequest`, listen for `AUDIOFOCUS_LOSS` / `AUDIOFOCUS_LOSS_TRANSIENT` / `AUDIOFOCUS_GAIN`). No telephony API, no permission. Use the answered-vs-declined timing heuristic (Pattern 3). This also covers alarms (alarm ringing = `AUDIOFOCUS_LOSS_TRANSIENT` on the alarm stream).
**Warning signs:** N/A if the telephony API is never touched. If a planner reintroduces it: a `SecurityException` crash on RecordingScreen mount on any device targeting 31+.

### Pitfall 3: MediaPipe `HandLandmarker` task-load latency / asset-path errors

**What goes wrong:** First `detect()` is slow (model load of the 7.8 MB bundle); wrong `setModelAssetPath` (must be the assets-relative path `"hand_landmarker.task"`, not an absolute file path, when bundled in `android/app/src/main/assets/`); `RunningMode` mismatch (IMAGE vs LIVE_STREAM) throws.
**Why it happens:** MediaPipe Tasks API is finicky about asset paths and running modes; cold-load of a 7.8 MB model is non-trivial.
**How to avoid:** Construct the `HandLandmarker` once (lazily, on first `detectHands` call) and reuse it (`getOrCreate()`). Use `BaseOptions.builder().setModelAssetPath("hand_landmarker.task")` with the asset under `android/app/src/main/assets/`. Set `RunningMode.IMAGE`, `numHands=2`, all min-confidences `0.5f`, CPU delegate (don't call `setDelegate(GPU)`). Imports: `com.google.mediapipe.framework.image.BitmapImageBuilder`, `com.google.mediapipe.tasks.core.BaseOptions`, `com.google.mediapipe.tasks.vision.core.RunningMode`, `com.google.mediapipe.tasks.vision.handlandmarker.{HandLandmarker, HandLandmarkerOptions}`. The HAND-12 pre-warm (a throwaway `takePhoto()`) plus the first real `detectHands()` warm both pipelines. Run the `HandLandmarker` work on `Executors.newSingleThreadExecutor()` (figure pattern) so it never blocks the bridge thread.
**Warning signs:** First gate detection takes >1 s; `IllegalStateException`/`MediaPipeException` on `detect()`; `landmarks()` always empty.

### Pitfall 4: VisionCamera 4.7.3 ↔ new-architecture / worklets / orientation-locker interactions

**What goes wrong:** VC 4.x on RN 0.83 new-arch can hit autolinking/codegen issues; the V4 worklets dep is `react-native-worklets-core@1.6.3` (NOT `react-native-worklets`) — mixing them breaks the build. `react-native-orientation-locker`'s README doesn't mention New-Arch/Fabric compatibility (it works via the legacy module system; in practice it functions under new-arch's interop layer but the planner should confirm at install). Conditionally rendering `<Camera>` vs `isActive={false}` have different teardown behaviour. `react-native-reanimated@3.16.x` + RN 0.83 new-arch is the supported pairing — 3.17+ is also out (latest 3.x is 3.19.5) but stay ≤3.16.x per STACK.md.
**Why it happens:** VC 4.x predates some new-arch stabilization; the worklets package split is a known footgun; orientation-locker is a legacy-style module.
**How to avoid:** Use exactly the locked stack (`vision-camera@4.7.3` + `worklets-core@1.6.3` + `reanimated@~3.16.7`; Skia ≥1.2.1 only if VC demands it as a peer). Read `.planning/research/STACK.md` "Mobile — Camera" recipe and `PITFALLS.md` for new-arch interactions. Don't pull in `react-native-worklets`. For orientation-locker: add the `MainActivity.onConfigurationChanged()` override + the `android:configChanges` manifest attr + `OrientationActivityLifecycle.getInstance()` in `MainApplication.onCreate` exactly as the README says; confirm a clean Android build. In `vitest.setup.ts`, add mocks for `react-native-vision-camera`, `react-native-tts`, `react-native-fs`, `react-native-orientation-locker` (reanimated + haptic-feedback + svg + mmkv are already mocked).
**Warning signs:** Codegen errors on build; `Worklets` undefined at runtime; preview black on some devices; rotation lock not honoured (forgot the manifest attr).

### Pitfall 5: `EmitterSubscription` leaks on RecordingScreen unmount

**What goes wrong:** RecordingScreen subscribes to `HumynCapture` events (5: `onSegmentStart`/`onSegmentComplete`/`onSessionStop`/`onThermalAbort`/`onError`) + `HumynPhoneState` + `HumynBattery` + AppState + orientation listeners. If any aren't `.remove()`d on unmount, you get duplicate handlers / memory leaks (Phase 3 JSDoc T-3.3-04 warns explicitly: every `on*(listener)` helper returns an `EmitterSubscription` the caller MUST `.remove()`).
**How to avoid:** Every subscription created in a `useEffect` returns a cleanup that `.remove()`s it. `useRecordingLifecycle` owns this discipline for the lifecycle sources; RecordingScreen owns it for the HumynCapture/VC sources. On the Kotlin side, `HumynBattery`/`HumynPhoneState` must unregister their receiver/listener on `onCatalystInstanceDestroy` (or expose explicit `start()`/`stop()` that RecordingScreen calls in its effect).
**Warning signs:** Stop fires twice; battery alert fires after leaving the screen; growing listener count in dev warnings.

### Pitfall 6: Brightness restore missed on an abnormal exit

**What goes wrong:** Brightness drops to 5% at gate exit; if the screen unmounts via a path that doesn't run `stop()` (crash, force-navigation, error), brightness stays at 5%.
**How to avoid:** Restore brightness in BOTH the `stop()` handler AND the RecordingScreen unmount cleanup. Use `screenBrightness = BRIGHTNESS_OVERRIDE_NONE` (`-1f` / `HumynScreenBrightness.set(-1)`) to restore the system default rather than caching a prior value. (The per-window override also auto-resets when the window/activity is destroyed — but a force-navigation within the same activity won't trigger that, hence the explicit restore.)
**Warning signs:** Screen stays dim after leaving the recording surface.

### Pitfall 7: `__DEV__` debug affordance leaking into production

**What goes wrong:** The non-practice debug long-press on TasksPlaceholder ships in the `apkRollout`/`playStore` build.
**How to avoid:** Wrap the _entire_ press handler (not just the navigation call) in `if (__DEV__) { ... }`. Add a quick test asserting the handler is undefined / the affordance absent when `__DEV__` is false. Production builds set `__DEV__ === false` → Metro dead-code-eliminates the block.
**Warning signs:** A reviewer finds a long-press shortcut in a release build.

### Pitfall 8: `computeInitialRoute` composition order

**What goes wrong:** The new per-account tutorial-flag check is composed incorrectly with the existing compat-signature gate — e.g. tutorial-done users get sent through compat again, or compat-failed users get the tutorial.
**How to avoid:** Order the checks: (1) no user/JWT → onboarding/splash; (2) compat not passed → onboarding/compat; (3) tutorial not done for this `sub` → onboarding/RigTutorial; (4) else → MainTabs. Pin with the existing `initialRoute` test pattern (add cases for the new branch). Read `apps/mobile/src/state/initialRoute.ts` for the actual signature before composing.
**Warning signs:** Existing `computeInitialRoute` tests go red; a returning user lands on RigTutorial; a compat-failed user lands on RigTutorial.

### Pitfall 9: `Camera.takePhoto()` cold-start latency leaves the gate ring stuck at 0 (PITFALLS.md Pitfall 9)

**What goes wrong:** On VC 4.x, the first `takePhoto()` after camera init can take 1–4 s (separate still-capture pipeline + JPEG-encoder buffer allocation). The `gate.loading` spinner shows, but the accumulator can't advance — users see a stuck ring. takePhoto can also hang if called before `onInitialized` (VC issue #2020).
**How to avoid:** HAND-12 pre-warm — after `onInitialized` fires (and before/at the moment the user can tap record), fire one throwaway `takePhoto()` and discard it (~3 MB peak, ~200 ms). Bind takePhoto behind `onInitialized`. Consider `takeSnapshot()` (preview-grab, ~16 ms) as a latency fallback if cold `takePhoto()` is still too slow on ₹30K devices — though the spec says `takePhoto()`.
**Warning signs:** `recording_gate_started → recording_gate_passed` median > 4 s (target is ~2 s wall clock); bitmap memory spikes to 30+ MB on the first `takePhoto()` (means full-res photo — see Pitfall 10).

### Pitfall 10: Bitmap memory pressure (PITFALLS.md Pitfall 10)

**What goes wrong:** VC `takePhoto()` returns the sensor's full resolution by default (12 MP × 4 bytes ARGB ≈ 48 MB); `BitmapFactory.decodeFile()` in `HandDetector` is another ~48 MB; multiply by gate cadence and you can allocate 240 MB/s. ₹30K phones (4–6 GB RAM) OOM and lose the session.
**How to avoid:** (a) On the `<Camera>`, set `photoQualityBalance="speed"` (and if VC 4.7.3 exposes a `photo` format constraint, prefer a small photo format). (b) In `HumynHandDetectorModule.kt`: decode with `BitmapFactory.Options { inPreferredConfig = Bitmap.Config.RGB_565 }` (half the memory of ARGB_8888) and downscale to 320×240 (`Bitmap.createScaledBitmap(decoded, 320, 240, true)` — MediaPipe binary detection works fine at that size). (c) Call `bitmap.recycle()` (and the scaled one if different) in a `finally` — the JS GC won't reclaim native bitmap memory in time. (d) Profile peak memory during the gate on the lowest-RAM target device.
**Warning signs:** Crashlytics OOM crashes scoped to the gate; native heap > 200 MB during the gate.

### Pitfall 11: OEM battery managers / camera quirks (PITFALLS.md Pitfall 7)

**What goes wrong:** Xiaomi MIUI / Oppo-Realme ColorOS / Vivo FunTouch / Samsung OneUI aggressively kill foreground services and don't honour the standard `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` API; some revert the exemption on app update. The FGS (HumynCapture's, Phase 3) and the new audio-focus/battery listeners can be killed on screen-off on aggressive ROMs. Some OEMs also default to a different camera than the one compat picked.
**Why it happens:** OEMs win battery benchmarks by killing background work; no commercial incentive to honour AOSP.
**How to avoid:** Phase 4 doesn't own the OEM-whitelisting walkthrough (that's the Phase 5/onboarding "OEM whitelisting" roadmap item), but Phase 4 should: (a) read the camera lens from `compat.lastResult.v1.checks.ultrawideDfov.cameraId` and pass it explicitly to VC (D-CAM-03) — don't trust VC's default device selection on OEM-quirky devices; (b) test the §10 lifecycle edges on at least one non-Pixel OEM device if available, and document known-quirky behaviour from `PITFALLS.md` Pitfall 7 if not. The FGS-survival problem is Phase 3's + Phase 5's; Phase 4 just needs the recording to _start_ correctly.
**Warning signs:** Call-answered doesn't stop the recording on a Xiaomi/Oppo test device; the gate sees the wrong camera POV.

### Pitfall 12: Skin-tone bias in the hand-gate (PITFALLS.md Pitfall 8) — telemetry must support tuning

**What goes wrong:** MediaPipe's hand model false-negatives on Fitzpatrick V/VI under warm-low-light (typical Indian-kitchen 2700K bulbs); also on gloves, henna, bandages, wet hands; false-positives near hot surfaces. The gate never advances → the user taps Skip every recording → a quiet but persistent "the defaults aren't tuned for me" signal. Even friction-free Skip is a relative-friction differential.
**How to avoid:** (a) Skip link visible from t=0 with zero friction (already in the spec — confirm). (b) HAND-14: instrument `recording_gate_skipped` with the device locale (`en-IN` vs `pt-BR`) AND a coarse skin-tone _proxy_ — log the average frame Y-channel luminance at gate start (correlates with both ambient brightness and skin tone; does NOT identify users; do NOT log image data — that's PII). (c) `minHandDetectionConfidence` is a Remote Config key (HAND-11) so it can be lowered from 0.5 → 0.3 → even 0.1 post-launch if Skip rate > 30% in a locale (the gate is one-shot pre-record; false-positives just let users start sooner — no data-quality cost). (d) Optionally: if the gate's been at counter=0 for >4 s, show a small "Try better lighting?" link below the prompt (not gated on it).
**Warning signs:** `recording_gate_skipped` > 20% in any locale; Skip-rate correlated with `Build.MANUFACTURER`; support tickets about "the camera doesn't see my hands".

### Pitfall 13: HumynCapture's `<60s` discard contract — confirm before relying on it (REC-07)

**What goes wrong:** REC-07 says "<60 s recordings are discarded, never persisted, with toast 'Recording too short — discarded.'". Who owns the discard — HumynCapture (delete the files at `stop()` when `durationMs < 60_000`), or RecordingScreen (call `stop()`, then... the files already landed in `recordings/`)? If neither, a sub-60s segment leaks into `recordings/` and Phase 5 uploads it.
**How to avoid:** Read Phase 3's `03-CONTEXT.md` D-FS-* and `idea-brief.md §5.8` "<60 seconds rule" — confirm whether HumynCapture itself discards sub-60s segments at finalize, or whether JS must do the cleanup. If HC owns it: RecordingScreen just shows the toast. If JS owns it: RecordingScreen must `RNFS.unlink` the triple after `onSegmentComplete` reports `durationMs < 60_000` — or, cleaner, escalate to Phase 3 to own the discard (it already owns the directory layout + the app-launch sweep). The `recState.cap` of `60_000` for practice is a separate thing (the practice hard-cap *upper* bound, not the *minimum\*). Note practice has NO minimum — a sub-60s practice still routes to PracticeComplete.
**Warning signs:** A 30-s test recording shows up in History (Phase 6) or gets uploaded (Phase 5).

### HumynHandDetector — Kotlin module (mirrors `figure-app-hands.md` + STACK.md recipe §3, with HAND-13 memory hygiene)

```kotlin
// HumynHandDetectorModule.kt — package ai.humynlabs.capture.handdetector
import android.graphics.Bitmap
import android.graphics.BitmapFactory
import com.facebook.react.bridge.*
import com.google.mediapipe.framework.image.BitmapImageBuilder
import com.google.mediapipe.tasks.core.BaseOptions
import com.google.mediapipe.tasks.vision.core.RunningMode
import com.google.mediapipe.tasks.vision.handlandmarker.HandLandmarker
import com.google.mediapipe.tasks.vision.handlandmarker.HandLandmarkerOptions
import java.util.concurrent.Executors

class HumynHandDetectorModule(ctx: ReactApplicationContext) : ReactContextBaseJavaModule(ctx) {
  override fun getName() = "HumynHandDetector"
  private val executor = Executors.newSingleThreadExecutor()
  @Volatile private var landmarker: HandLandmarker? = null

  // HAND-11: confidence is a Remote Config key; pass it from JS via configure(), default 0.5f.
  private fun getOrCreate(minConf: Float): HandLandmarker = landmarker ?: synchronized(this) {
    landmarker ?: HandLandmarker.createFromOptions(
      reactApplicationContext,
      HandLandmarkerOptions.builder()
        .setBaseOptions(BaseOptions.builder().setModelAssetPath("hand_landmarker.task").build()) // CPU delegate (default)
        .setRunningMode(RunningMode.IMAGE)
        .setNumHands(2)
        .setMinHandDetectionConfidence(minConf)
        .setMinHandPresenceConfidence(0.5f)
        .setMinTrackingConfidence(0.5f)
        .build()
    ).also { landmarker = it }
  }

  @ReactMethod
  fun detectHands(path: String, minConfidence: Double, promise: Promise) {
    executor.execute {
      var decoded: Bitmap? = null
      var scaled: Bitmap? = null
      try {
        val opts = BitmapFactory.Options().apply { inPreferredConfig = Bitmap.Config.RGB_565 } // HAND-13: half the memory
        decoded = BitmapFactory.decodeFile(path, opts)
          ?: throw IllegalArgumentException("decodeFile returned null for $path")
        scaled = Bitmap.createScaledBitmap(decoded, 320, 240, true)                              // HAND-13: 320×240
        val result = getOrCreate(minConfidence.toFloat()).detect(BitmapImageBuilder(scaled).build())
        promise.resolve(result.landmarks().size)                                                  // hand count only: 0 / 1 / 2
      } catch (e: Exception) {
        promise.reject("HAND_DETECT_FAILED", e)                                                   // JS treats reject as a miss
      } finally {
        scaled?.takeIf { it !== decoded }?.recycle()
        decoded?.recycle()                                                                        // HAND-13: explicit recycle
      }
    }
  }

  @ReactMethod fun cleanup(promise: Promise) {
    synchronized(this) { landmarker?.close(); landmarker = null }; promise.resolve(null)
  }
}
```

> The `minConfidence` param means re-creating the landmarker if it changes — simplest is: JS calls `cleanup()` then re-`detectHands()` if the Remote Config value differs from the cached one. The planner can simplify (Remote Config rarely changes mid-session) to: read the RC value once at RecordingScreen mount, pass it to every `detectHands` call, ignore changes within a session.

```typescript
// ulid: a tiny inline ULID or react-native-uuid (already a dep — uuid v4 is fine for a temp filename)

async function runGateCheck(camera: Camera, dispatch: Dispatch<RecAction>, minConf: number) {
  // [ASSUMED] VC 4.7.3 takePhoto signature — verify against the installed react-native-vision-camera types.
  // Confirmed via Context7 v4.7.2 docs: takePhoto({flash:'on'|'off'|'auto', enableShutterSound, enableAutoRedEyeReduction}) → PhotoFile{path,width,height,orientation,...}

    RNFS.unlink(dest).catch(() => {}); // delete on resolve (pass/miss/error)
  }
}
```

### en-IN TTS voice fallback — JS (Pattern 4, REC-14)

```typescript
import Tts from 'react-native-tts';
// react-native-tts voices(): [{ id, name?(iOS only), language(BCP-47), quality(300|500), latency?(100-500,Android), networkConnectionRequired?(Android), notInstalled?(Android) }]
// No gender field — heuristic on language + name/id.
const looksFemale = (v: any) =>
  /female|woman|-fem|fenrir|salli|joanna|amy|raveena/i.test(`${v.name ?? ''}${v.id ?? ''}`);
export async function pickAndSetEnInVoice() {
  await Tts.getInitStatus(); // resolves when the TTS engine is ready
  let voices: any[] = [];
  try {
    voices = await Tts.voices();
  } catch {
    /* Android <21 returns [] — fall through to engine default */
  }
  const usable = voices.filter((v) => !v.notInstalled);
  const id =
    usable.find((v) => v.language === 'en-IN' && looksFemale(v))?.id ?? // 1. en-IN female-ish
    usable.find((v) => v.language === 'en-IN')?.id ?? // 2. any en-IN
    usable.find((v) => v.language === 'en-US' && looksFemale(v))?.id ?? // 3. en-US female-ish
    usable.find((v) => (v.language ?? '').toLowerCase().startsWith('en'))?.id; // 4. first en-*
```

### Known threat patterns for this stack

| Pattern                                                                                  | STRIDE                                    | Standard mitigation                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Debug affordance shipped to production                                                   | Elevation of privilege / Info disclosure  | `if (__DEV__)` wrapping the _entire_ press handler; test absence in release builds (Pitfall 7).                                                                                                          |
| Camera frames left in cache                                                              | Information disclosure                    | `cacheDir` only; delete on each gate-check resolve; app-launch sweep clears `cacheDir/hand-gate/*` stragglers; exclude from backup.                                                                      |
| Logging the JWT / `sub` / image data                                                     | Information disclosure                    | Never log auth material; HAND-14 logs a luminance proxy not the image; Crashlytics breadcrumbs scrubbed.                                                                                                 |
| Accidentally adding `READ_PHONE_STATE` / `ACCESS_NOTIFICATION_POLICY` / `WRITE_SETTINGS` | Elevation of privilege / Spec violation   | `HumynPhoneState` uses `AudioManager` only; `HumynScreenBrightness` uses the per-window override only; manifest audit in CI (Phase 2 already has `verify-merged-manifests.sh`).                          |
| Crash-recovery payload trusted blindly                                                   | Tampering (low — app-internal)            | Validate `recovered` is `string[]`; recovered segments still go through Phase 5's verification path.                                                                                                     |
| Listener/receiver/audio-focus-request leaks → battery drain / duplicate stops            | DoS (self-inflicted)                      | Unregister every receiver/callback/focus-request on module invalidate & RecordingScreen unmount (Pitfall 5).                                                                                             |
| `start(opts)` constructed with `contributor.consent !== true`                            | Spec evasion (consent bypass in metadata) | The Phase-3 Kotlin side re-validates with `z.literal(true)` — a non-true value makes `start()` reject. Phase 4's call site must source `consent` from the verified Phase-2 `/me` data, never default it. |

> Phase 4's attack surface is small — no network, no new auth, no new persisted secrets. The real "security-ish" concerns are (a) not leaking the debug affordance, (b) not leaving camera frames around, (c) not logging auth material or image data, (d) not accidentally adding forbidden permissions, (e) sourcing `contributor.consent` honestly.
