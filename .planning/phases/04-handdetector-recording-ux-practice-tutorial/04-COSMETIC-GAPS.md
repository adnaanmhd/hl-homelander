## New from the 2026-05-12 re-walk (the `/gsd-debug phase4-smoke-fixes` round)

- **Alert-cue tones don't play (`HumynBeep.playTone`) — likely device media volume, not a code bug.** During the re-walk, the battery-15 % **520 Hz beep** and the thermal-abort **descending 440→560→680 Hz tone sequence** were inaudible, while the pill / haptic / voice-cue / auto-stop all fired on both paths (so the user is unmistakably alerted; only the audio embellishment is missing). Logcat showed the device's media-volume scalar at ~3.6 % (`AHal::Waves: ... MaxVolume: 0.0362078`), so this is almost certainly just the test device's media volume being turned down — the recording-cue TTS rides a louder path and was audible. **Action:** re-check with the device's media volume up; only if the tones are still silent at full volume is there a real `HumynBeep` / SoundPool bug to chase. (The 2026-05-12 first walk's §6 PASSED list says the 520 Hz beep was audible then — consistent with it being device state.)
- **Battery-critical (5 %) / thermal mid-record stop leaves you on RecordingScreen-'ready', not Home.** When a mid-record stop fires from battery≤5 % (REC-11) or a thermal abort, the recording finalizes and — for a <60 s take — shows the "Recording too short — discarded." toast and `RESET_FOR_FRESH`'s back to the 'ready' substate on the same screen, rather than navigating to Home. The normal sub-60 s discard flow does the same (deliberate — "re-pressing record starts a fresh recording with no countdown", REC-05), so it's not obviously wrong, but for a _device-distress_ stop it's debatable whether the user should be left one tap away from another recording (the <5 % start-guard would refuse the next one anyway). Decide whether device-distress stops should bounce to Home.
- **Crash-recovery Home toast uses a 15 s duration as a workaround.** The "Recording recovered after force-quit — uploading." toast fires from `App.tsx`'s mount effect — i.e. while the `SplashScreen` route is still doing its bootstrap (version check / RemoteConfig / Play Integrity, up to the ~8 s `bootstrap_hard_timeout`). `<ToastHost />` is a sibling of the navigator so the pill persists across the splash → Home transition, but the original 5 s duration meant it had faded before Home appeared ("no Home toast appeared" was the first walk's bug 3(a) — it WAS shown, just on the splash). Bumped to 15 s in `bootRecoveryListener.ts` so it spans the bootstrap and is still on screen for a few seconds on Home (verified on the re-walk). **Proper fix:** stash the recovered list and trigger the toast from the post-bootstrap navigation / Home mount, so it's a normal-duration toast at the right moment.
- **Force-quit recovery only salvages a recording that crossed a 30 s `moof` flush.** `FragmentedMuxerWrapper` flushes a `moof` fragment every 30 s (CAP-02 / `idea-brief.md §6.6`), so a force-quit / OS-evict in the first ~30 s leaves only the `ftyp`+`moov` init segment on disk (~778 bytes) — `CaptureLaunchSweep` correctly classifies that as unrecoverable and discards the stub + the IMU csv + the `.session.json` sidecar (no leftover orphan, no misleading "recovered" toast). A crash _after_ the first flush leaves a real ~30 s+ fragment → re-finalized into a usable `{base}.{mp4,csv,json}` triple (with degenerate `imu_video_drift_*` / `imu_min_rate_*` / `duration_seconds:0`, since those can't be recomputed from a crash-truncated partial). This is inherent to the fragmented-MP4 design, not a bug — but worth a line in the D-LIFE-04 / Phase-5-upload notes (Phase 5's upload path should tolerate a recovered segment's `duration_seconds: 0` and null drift fields).
