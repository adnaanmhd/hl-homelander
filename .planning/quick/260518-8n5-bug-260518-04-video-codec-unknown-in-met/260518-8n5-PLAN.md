<objective>
Fix BUG-260518-04 — every segment from the 2026-05-18 E2E walk stamped `metadata.metadata.video_codec = "unknown"` instead of `"hevc"`. The root cause is `MetadataComposer.buildVideoReport` (MetadataComposer.kt:500) reads the codec MIME from the encoder's `OUTPUT_FORMAT` snapshot only — on the Pixel 8a / 10a encoders that key resolves to `null`, falls through `mimeToCodecToken(null)`, and stamps `"unknown"`. The MediaExtractor track-header read in the same function already opens the muxed MP4 and reads each track's `KEY_MIME` to find the video track — that MIME is the spec-compliant CAPTURE-QA-01 truth source (it's what was actually muxed into the MP4) and we are throwing it away. Capture it and use it as the primary codec source.

Purpose: restore truthful `video_codec` metadata for the training pipeline. CAPTURE-QA-01 is the canonical "metadata reflects measured reality" contract; this regression slipped past the comment-stripped grep gate (which only catches inline literals — it can't catch a `null`-and-fallback chain that produces `"unknown"`).

Output: a 2-task atomic fix — (1) tighten `buildVideoReport` to derive codec from MediaExtractor track-header MIME with the encoder OUTPUT_FORMAT MIME as a secondary source and `HevcEncoder.MIME` as a last-resort fallback; (2) add a regression test proving codec derives correctly even when `encoder.outputFormat` carries no `KEY_MIME`.
</objective>
