# Quick Task 260518-8n5: BUG-260518-04 video_codec=unknown in metadata Summary

`metadata.metadata.video_codec` now derives from a 3-source priority chain (MediaExtractor track-header MIME → encoder OUTPUT_FORMAT MIME → configured `HevcEncoder.MIME`) instead of reading only `encoder.outputFormat.getString(KEY_MIME)` — which returns `null` on Pixel 8a / 10a `apkRollout` build `22ffec5` and stamped every segment from the 2026-05-18 E2E walk with `"unknown"`.

## Root cause

`MetadataComposer.buildVideoReport` (MetadataComposer.kt:500 pre-fix) read the codec MIME from a single source — the encoder's OUTPUT_FORMAT snapshot:

```kotlin
val of = try { encoder?.outputFormat } catch (_: Throwable) { null }
val codec = mimeToCodecToken(of?.getString(MediaFormat.KEY_MIME))
```

On the Pixel 8a / Pixel 10a `apkRollout` 22ffec5 encoders, that `getString(KEY_MIME)` returned `null` even though every OTHER OUTPUT_FORMAT-derived field populated correctly — `video_profile = "main"`, `bitrate_bps = 8000000`, `bitrate_mode = "cbr"`, `gop = 30`, `b_frames = false`, `color_space = "bt709"`, `color_depth_bits = 8`. Some Android encoders expose MIME only on the INPUT format (the one passed to `configure()`), not on the OUTPUT_FORMAT snapshot.

The `null` MIME fell through `mimeToCodecToken(null)` → `"unknown"`. Evidence in the field: 15/15 verified segments from the 2026-05-18 walk on build `22ffec5` stamped `video_codec: "unknown"` (BUG-260518-04 in `E2E-WALK-BUGS-260518.md`).

The kicker: the MediaExtractor loop in the same function was already reading each track's `KEY_MIME` (to find the video track) and discarding the value. That MIME is the spec-compliant CAPTURE-QA-01 truth source — it's what was actually committed to the MP4 the training pipeline will read.

## Fix

New pure-fn helper alongside the existing `mimeToCodecToken`:

```kotlin
internal fun chooseCodecToken(
    extractorMime: String?,
    encoderMime: String?,
    configuredMime: String?,
): String = mimeToCodecToken(extractorMime ?: encoderMime ?: configuredMime)
```

`buildVideoReport` now:

1. **Captures** `extractorVideoMime` from the first video track's `KEY_MIME` (instead of `continue`-discarding it after the `startsWith("video/")` check).
2. **Resolves** the codec via `chooseCodecToken(extractorMime = extractorVideoMime, encoderMime = of?.getString(MediaFormat.KEY_MIME), configuredMime = HevcEncoder.MIME)`.

Priority chain:

| Rank | Source                                      | Why                                                                                                                                                                                                               |
| ---- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `MediaExtractor.getTrackFormat(i).KEY_MIME` | Highest authority — what was committed to the MP4 the training pipeline reads.                                                                                                                                    |
| 2    | `encoder.outputFormat.getString(KEY_MIME)`  | Authoritative when populated; `null` on Pixel 8a / 10a (the BUG-260518-04 case).                                                                                                                                  |
| 3    | `HevcEncoder.MIME` (configured constant)    | The value LITERALLY passed to `createEncoderByType(MIME)` — cannot be wrong by construction.                                                                                                                      |
| —    | All three `null` → `"unknown"`              | Only reachable if MP4 is unreadable AND encoder is silent AND no configured constant. In production the upstream resolution gate (`width<1920` → `resolution_dropped`) already canceled the segment in that case. |

CAPTURE-QA-01 compliance: every source in the chain is a derived fact. `HevcEncoder.MIME` is not a duplicate of `idea-brief.md §2.1` — it's the encoder's own identity (the string passed to `MediaCodec.createEncoderByType`), so the encoder cannot have produced any other codec.

CAPTURE-QA-03 compliance: no inline `"hevc"` literal added to `.put("video_codec", ...)` in `compose()`. The comment-stripped grep gate (`compose() has no inline spec literals`) still passes.

## Tests

Five new `@Test` methods in `MetadataComposerLiteralsTest`:

| #   | Test                                                                                              | Inputs (extractor / encoder / configured) → Expected           |
| --- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1   | `chooseCodecToken — extractor MIME wins when present`                                             | `"video/hevc"` / `null` / `"video/hevc"` → `"hevc"`            |
| 2   | `chooseCodecToken — falls back to encoder MIME when extractor is null (BUG-260518-04 regression)` | `null` / `"video/hevc"` / `"video/hevc"` → `"hevc"`            |
| 3   | `chooseCodecToken — falls back to configured MIME when both extractor and encoder are null`       | `null` / `null` / `MediaFormat.MIMETYPE_VIDEO_HEVC` → `"hevc"` |
| 4   | `chooseCodecToken — returns unknown only when all three sources are null`                         | `null` / `null` / `null` → `"unknown"`                         |
| 5   | `chooseCodecToken — extractor MIME beats a conflicting encoder MIME`                              | `"video/avc"` / `"video/hevc"` / `"video/hevc"` → `"h264"`     |

All five exercise the pure-fn helper directly — Robolectric can't drive a real `MediaCodec` / `MediaExtractor`, but pure-fn coverage is the same pattern used by the existing `mimeToCodecToken` / `bitrateModeToToken` / etc. token mappers in the same composer.
