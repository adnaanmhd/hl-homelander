## Patterns introduced

**Pattern 63 — controlled-prop choice picker grafted onto a free-text edit primitive.** Adding an optional `options?: string[]` to `InlineEditField` lets the same component handle both free-text rows (Name, Age) and constrained-enum rows (Gender) with no API churn at consumer call sites. The presence of `options` is the discriminator: rendering branches between TextInput inline-edit and a Modal-based picker. Reusable for any future Phase 5+ field that needs a small constrained set (e.g. notification cadence, payout threshold tiers).

**Pattern 64 — transient user slice with two write-paths (sign-in + /me) and write-through caching.** appStore's `user` slice is populated immediately by SignupScreen's signInWithGoogle (Google returns name + email + photo URL) AND refreshed by ProfileScreen's `/me` on mount. Both writes go through the same `setUser` action; readers (TopBar, future surfaces) don't care which path populated. This handles the "existing-session-without-store-slice" case naturally: visiting Profile once self-heals the cache. Critical: the slice is NOT persisted to MMKV — backend updates flow through `/me` and would otherwise stale-cache. Reusable for any future user-display data (e.g. Phase 6 lifetime stats, Phase 5 payout-status badges).

**Anti-pattern recorded: blanket `git add <file>` when the working tree contains intentionally-uncommitted changes.** Per `feedback_functionality_first_during_smoke.md`, `apps/mobile/src/screens/signup/SignupScreen.tsx` carried Phase 3 W1 cosmetic-backlog work in the working tree throughout today's smoke walk. Adding the file with my `setUser` additions silently picked up the cosmetic content too. Fix: when the smoke walk preserves uncommitted backlog files, surgical hunk staging is required — either via `git add -p` interactive selection OR (the path I used) save-cosmetic-version → restore-from-HEAD → reapply-only-my-edits → stage → commit → restore-cosmetic-version. Future quick tasks that touch backlog files should follow this protocol.
