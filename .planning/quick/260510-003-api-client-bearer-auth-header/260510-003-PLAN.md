# Quick Task 260510-003: apiClient bearer-header attachment

## Root cause

`apps/mobile/src/services/api.ts` defines `apiClient` with `post`, `postNoBody`, `getJson`, `get`, `patch`, `delete`, `postMultipart` — and **none** of them read the JWT from MMKV or attach an `Authorization: Bearer <jwt>` header to outbound requests.

The JWT is stored at MMKV key `KEYS.AUTH_JWT` (`'auth.jwt.v1'`) by `services/auth.ts:150` after a successful sign-in, and accessor `getStoredJwt()` exists in the same file. But `api.ts` never imports MMKV or the JWT accessor.

Backend `requireAuth` plugin gate runs on every authenticated route (Phase 1 plan 01-04 + 01-05). With no `Authorization` header on the wire, it returns:

```
{"type":"https://humyn-app.io/problems/unauthorized","title":"Unauthorized","status":401,"detail":"Missing or invalid JWT","instance":"<request-id>"}
```

This affects every authenticated mobile endpoint (Phase 2 surface):

- `GET /me` (PROF-01..05, plan 02-17) — surfaced by §7 smoke walk
- `PATCH /me` (AUTH-08, plan 02-17) — would 401 on profile-name edit
- `DELETE /me?confirm=DELETE` (AUTH-09, plan 02-19) — would 401 on delete-account
- `POST /feedback` (HELP-05, plan 02-18) — would 401 on submit-feedback

It does NOT affect the bootstrap routes (`/auth/google`, `/app/version`) which intentionally do not require auth.

## Why this didn't show up earlier

Plans 02-17 / 02-18 / 02-19 all ship `code-ready-smoke-deferred` per STATE.md. Their unit tests mock `apiClient` whole-cloth — `vi.mock('../../src/services/api', () => ({ apiClient: { get: vi.fn() } }))` — so the real fetch path never runs in CI. Same pattern as today's other fix-forward bugs (auth nonce, IMU permission, DeviceCaps): tests pass, smoke walk surfaces the gap.

Compounded by: there's no `api.test.ts`. The transport layer has zero direct tests; everything verifying it has been mocked away.

## Fix design

### Step 1 — Read JWT from MMKV inside apiClient

Add a private helper that returns `{ authorization: 'Bearer <jwt>' }` if the JWT is present in MMKV, or `{}` if not. Spread the result into the headers map of every request method.

```ts
import { secureMmkv } from '../state/mmkv';
import { KEYS } from '../state/keys';

function bearerHeader(): Record<string, string> {
  const jwt = secureMmkv.getString(KEYS.AUTH_JWT);
  return jwt ? { authorization: `Bearer ${jwt}` } : {};
}
```

### Step 2 — Attach header to all six methods

For each of `post` / `postNoBody` / `getJson` / `patch` / `delete` / `postMultipart`, spread `...bearerHeader()` into the headers object:

```ts
const headers: Record<string, string> = { 'content-type': 'application/json', ...bearerHeader() };
```

`getJson` had `headers: { accept: 'application/json' }` literal; convert to a `headers` const so the spread works. `postNoBody` had no headers map at all; introduce one.

### Why "always attach" instead of an opt-in `auth: true` flag

- Simpler call sites — no per-call `{ auth: true }` ceremony.
- The two unauthenticated routes (`/auth/google`, `/app/version`) accept (and ignore) a stray Bearer header — Fastify's `requireAuth` is per-route-opt-in, not a deny-list.
- Pre-sign-in calls (no JWT in MMKV) get an empty `{}` spread — no header, no behavior change.
- @fastify/rate-limit's authenticated-tier keyGenerator (Pattern 26) does its own best-effort jwtVerify; sending a Bearer to /auth/google would cause it to key on `sub` instead of IP, but that's actually MORE correct (per-user rate-limit) and aligns with the auth route's own rate-limit semantics.
