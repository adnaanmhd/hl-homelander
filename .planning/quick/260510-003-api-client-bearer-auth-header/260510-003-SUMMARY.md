## Patterns introduced

**Pattern 60 — apiClient bearer-header attachment via direct MMKV read.** When a transport-layer client needs to attach an authentication header sourced from app state, read the state directly (here: `secureMmkv.getString(KEYS.AUTH_JWT)`) instead of importing the auth module — that auth module almost certainly imports the transport client for its bootstrap call (`POST /auth/google`), creating a circular dep. The "always-attach-if-present" semantic is also simpler than per-call `auth: true` opt-in: pre-sign-in calls naturally get an empty spread, and unauthenticated routes accept-and-ignore a Bearer header (Fastify's `requireAuth` is per-route opt-in, not deny-list). Reusable for any future Phase 5+ transport additions (e.g. signed-URL upload polling, hash-verify receipts).

**Anti-pattern recorded: 100%-mock service-layer tests miss transport-layer regressions.** Plans 02-17/02-18/02-19's tests `vi.mock('../../src/services/api', () => ({ apiClient: { ... vi.fn() ... } }))` — fully mocked client. This is fine for asserting service orchestration logic (idempotency-key generation, error-message synthesis, partial-result handling) but provides ZERO coverage of the actual fetch path. Future plans that ship transport-layer changes MUST include at least one `api.test.ts`-style direct test that spies on `globalThis.fetch` and asserts the request shape (URL, method, headers, body framing). Recommended addition to the gsd-pattern-mapper rules for future transport-touching plans.
